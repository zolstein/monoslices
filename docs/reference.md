# monoslices reference

This document describes the complete user-visible configuration and source rules for `monoslices`.

For installation, examples, motivation, and benchmark results, see the project [README](../README.md).

## Invocation

`monoslices` operates on the Go package in its current working directory:

```sh
go tool monoslices
```

The normal use is through `go generate`:

```go
//go:generate go tool monoslices
```

One invocation discovers every `//monoslices:generate` [directive](#directives) in the package and writes a single aggregate generated file.

### CLI flags

`monoslices` supports the following CLI flags:

| Flag       | Meaning                    |
| ---------- | -------------------------- |
| -out       | Generated output file name |
| -h / -help | Print help text            |

Positional arguments are rejected.

### Output files

The default output filename is `monoslices_gen.go`. The flag `-out=<file.go>` causes the command to output generated code to `<file.go>` instead.

The output must remain in the package directory. It must be an ordinary production `.go` filename. In particular, an output filename may not:

- end in `_test.go`;
- begin with `.` or `_`;
- imply a GOOS or GOARCH build constraint.

Output paths cannot escape the package directory through traversal or parent-directory symlinks.

Generated files contain the ownership comment `// Code generated by monoslices. DO NOT EDIT.` Generation may overwrite or delete such files.

Generation builds and formats the complete output before writing it. Source discovery, parsing, validation, generation, formatting, or write failures do not modify existing files.

## Directives

A directive names one or more specialization functions (predicates, equality functions, or comparators) and generates one or more operations.

### Syntax

A directive begins with the exact prefix `//monoslices:generate`.

For example:

```go
//monoslices:generate name=Records cmp=compareRecord
```

There is no space after `//`.

The complete grammar is:

```text
//monoslices:generate name=<identifier> [pred=<identifier>] [eq=<identifier>] [cmp=<identifier>] [byref=<mode>] [ops=<operations>]
```

Every directive must supply at least one of `pred`, `eq`, or `cmp`.

Assignments are separated by whitespace.

Each key may appear at most once. Unknown keys are errors. Keys may appear in any order.

Values are non-empty, unquoted and may not contain whitespace. Multiple values, where allowed, are specified as comma-separated lists of non-empty, non-duplicate elements.

### Keys

| Key     | Supported Values                           | Meaning                                                   |
| ------- | ------------------------------------------ | --------------------------------------------------------- |
| `name`  | Any valid, non-keyword Go identifier       | Prefix for generated operation names.                     |
| `pred`  | Any valid, non-keyword Go identifier       | Name of a unary predicate function: `func (E) bool`       |
| `eq`    | Any valid, non-keyword Go identifier       | Name of a binary equality function: `func (E1, E2) bool`  |
| `cmp`   | Any valid, non-keyword Go identifier       | Name of a binary comparator function: `func (E1, E2) int` |
| `byref` | `true`, `first`, or `second`               | Slice-element parameter positions to pass by reference.   |
| `ops`   | One or more valid [operation](#operations) | Operations to generate.                                   |

#### `name`

`name` must be a valid non-keyword Go identifier.

It is used exactly as written and is not pluralized or otherwise transformed:

```go
//monoslices:generate name=Records cmp=compareRecord
```

can generate:

```go
RecordsCompare
RecordsMin
RecordsSort
RecordsBinarySearch
```

Capitalization determines whether the generated declarations are exported.

## Specialization functions

Specialization functions named by `pred`, `eq`, or `cmp` must:

1. be package-level function declarations;
2. be declared in the same `.go` file as the directive that references them;
3. not be generic or variadic;
4. have a supported parameter and result shape.

### Predicates

A predicate has the shape:

```go
func(E) bool
```

For example:

```go
func isExpired(record Record) bool
```

### Equality functions

An equality function has the shape:

```go
func(E1, E2) bool
```

For example:

```go
func equalRecord(a, b Record) bool
```

### Comparators

A comparator has the shape:

```go
func(E1, E2) int
```

For example:

```go
func compareRecord(a, b Record) int
```

### Result types must be written directly

Predicate and equality functions must write their result type directly as `bool`. Comparator functions must write their result type directly as `int`. Other spellings — in particular, type aliases — are rejected:

```go
type Result = bool

func isRecord(Record) Result // unsupported
```

Named results are supported:

```go
func isRecord(Record) (ok bool)

func compareRecord(a, b Record) (result int)
```

## Type matching

`monoslices` uses the parameter types of specialization functions, as written in the source, when generating code.

Some operations require the specialization function parameters to share an [effective type](#effective-signature). Such functions are considered “homogeneous.” Others are considered “heterogeneous.”

For example, the following function is homogeneous:

```go
func compare(a, b Record) int
```

The effective types of both parameters must use the same normalized source spelling to be considered homogeneous.

This is treated as heterogeneous, even if `Left` and `Right` resolve to identical Go types:

```go
func compare(a Left, b Right) int
```

Formatting and redundant parentheses are normalized when comparing source spellings.

## Operations

The following operation names are accepted. Generated functions append the operation in Go casing to `name`.

| Operation       | Generated suffix | Function signature                   | Corresponding `slices` function |
| --------------- | ---------------- | ------------------------------------ | ------------------------------- |
| `contains`      | `Contains`       | `func(s []E) bool`                   | `slices.ContainsFunc`           |
| `index`         | `Index`          | `func(s []E) int`                    | `slices.IndexFunc`              |
| `delete`        | `Delete`         | `func(s []E) []E`                    | `slices.DeleteFunc`             |
| `compact`       | `Compact`        | `func(s []E) []E`                    | `slices.CompactFunc`            |
| `equal`         | `Equal`          | `func(a []E1, b []E2) bool`          | `slices.EqualFunc`              |
| `compare`       | `Compare`        | `func(a []E1, b []E2) int`           | `slices.CompareFunc`            |
| `min`           | `Min`            | `func(s []E) E`                      | `slices.MinFunc`                |
| `max`           | `Max`            | `func(s []E) E`                      | `slices.MaxFunc`                |
| `sort`          | `Sort`           | `func(s []E)`                        | `slices.SortFunc`               |
| `sort-stable`   | `SortStable`     | `func(s []E)`                        | `slices.SortStableFunc`         |
| `is-sorted`     | `IsSorted`       | `func(s []E) bool`                   | `slices.IsSortedFunc`           |
| `binary-search` | `BinarySearch`   | `func(s []E, target E2) (int, bool)` | `slices.BinarySearchFunc`       |

### Operation behavior

Generated operations have the same behavior and preconditions as their corresponding `slices.*Func` operations.

In particular, callers should rely on the `slices` contract for:

- which operations modify their input slice;
- clearing of obsolete tails by delete/compact operations;
- panic behavior for extrema on empty slices;
- comparator ordering requirements;
- stable-sort behavior;
- binary-search sorted-input requirements and insertion-index semantics.

The generated API removes the function parameter because the specialization function was selected at generation time.

### Operation applicability

Which operations are available depends on the specialization function’s [effective signature](#effective-signature).

| Type                     | Effective Signature | Applicable operations                                                        |
| ------------------------ | ------------------- | ---------------------------------------------------------------------------- |
| Predicate                | `func(E) bool`      | `contains`, `index`, `delete`                                                |
| Homogeneous equality     | `func(E, E) bool`   | `compact`, `equal`                                                           |
| Heterogeneous equality   | `func(E1, E2) bool` | `equal`                                                                      |
| Homogeneous comparator   | `func(E, E) int`    | `compare`, `min`, `max`, `sort`, `sort-stable`, `is-sorted`, `binary-search` |
| Heterogeneous comparator | `func(E1, E2) int`  | `compare`, `binary-search`                                                   |

A directive may supply more than one function role:

```go
//monoslices:generate name=Records pred=isRecord eq=equalRecord cmp=compareRecord
```

By default, all applicable operations are generated.

### Selecting operations with `ops`

Use `ops` to generate only selected operations:

```go
//monoslices:generate name=Records cmp=compareRecord ops=sort,binary-search
```

Every requested operation must be applicable to one of the functions supplied by that directive.

For example, these are invalid:

```go
// duplicate operation
//monoslices:generate name=Records cmp=compareRecord ops=sort,sort

// empty operation
//monoslices:generate name=Records cmp=compareRecord ops=sort,,max
```

Generated operations are emitted in canonical operation order, not the order in which they appear in `ops`.

## By-reference functions

`byref` operations pass selected slice elements to specialization functions by reference.

Given:

```go
func compareRecord(a, b *Record) int
```

this directive:

```go
//monoslices:generate name=Records cmp=compareRecord byref=true ops=sort
```

generates:

```go
func RecordsSort(s []Record)
```

and calls the comparator with addresses of slice slots:

```go
compareRecord(&s[i], &s[j])
```

### Modes

`byref` accepts three values:

- `true` selects every eligible parameter.
- `first` selects the first specialization-function parameter when it is eligible.
- `second` selects the second specialization-function parameter when it is eligible.

`byref` must select at least one eligible parameter in the directive’s generated operations. `second` mode has no effect on some operation types.

### Effective signature

`byref` changes the effective signature of a specialization function for the purposes of generated output signatures and determining homogeneity. Selected pointer parameters that receive slice elements are treated as the pointed-at type.

For example, one comparator can generate the following signatures:

```go
func compare(a *Elem, b *Key) int
//monoslices:generate name=NoByref cmp=compare ops=compare
//monoslices:generate name=ByrefTrue cmp=compare ops=compare byref=true
//monoslices:generate name=ByrefFirst cmp=compare ops=compare byref=first
//monoslices:generate name=ByrefSecond cmp=compare ops=compare byref=second
```

generates:

```go
func NoByrefCompare(a []*Elem, b []*Key) int
func ByrefTrueCompare(a []Elem, b []Key) int
func ByrefFirstCompare(a []Elem, b []*Key) int
func ByrefSecondCompare(a []*Elem, b []Key) int
```

Whether or not a parameter receives a slice element is a property of the operation. One specialization function may be treated differently in different operations.

### Explicit pointer syntax is required

A selected parameter must use explicit pointer syntax. Parenthesized pointer syntax is also supported:

```go
func compare(a, b *Record) int
func compare(a, b (*Record)) int
```

A name or alias whose underlying type is a pointer does not count as explicit pointer syntax:

```go
type RecordPtr = *Record
func compare(a, b RecordPtr) int // unsupported with byref=true
```

### Eligibility follows the operand

A parameter is eligible only when the generated algorithm supplies a slice element to it. Matching the slice element’s type does not make another argument eligible.

For binary search, the first comparator parameter receives a slice element and the second receives the caller’s target:

```go
func compareRecords(a, b *Record) int {
	// ...
}

//monoslices:generate name=Records cmp=compareRecords byref=true ops=binary-search
```

This generates:

```go
func RecordsBinarySearch(s []Record, target *Record) (int, bool)
```

and calls:

```go
compareRecords(&s[h], target)
```

`byref=second` is ineffective for a directive that generates only binary search because the second argument is not a slice element.

### Pointer lifetime and mutation

By-reference arguments point to element slots in the slice. Specialization functions should generally treat them as read-only and ephemeral. Writing through a pointer modifies the slice and may violate an operation’s invariants. Operations that overwrite elements can also make a retained pointer refer to a different logical element.

## Imported types

If a package-qualified name appears directly in a specialization function parameter type, the import must use an explicit alias.

Supported:

```go
import model "example.com/project/model"

func compare(a, b model.Record) int {
	// ...
}

//monoslices:generate name=Records cmp=compare
```

Unsupported:

```go
import "example.com/project/model"

func compare(a, b model.Record) int {
	// ...
}

//monoslices:generate name=Records cmp=compare
```

This restriction applies only when the imported qualifier appears directly in the spelling of the type in the specialization function signature.

A local named or aliased type may hide the imported qualifier:

```go
import "example.com/project/model"

type Record = model.Record

func compare(a, b Record) int {
	// ...
}

//monoslices:generate name=Records cmp=compare
```

This is supported because the function signature uses the package-local `Record`, not `model.Record`.

### Import conflicts

Explicit import aliases used by specialization function types are preserved exactly.

If a qualifier used directly in a preserved parameter type has explicit imports mapping it to different paths, generation fails rather than choosing one by import order. Repeated bindings of the same alias to the same path remain unambiguous.

Different aliases for the same import path are supported when both are required by specialization function types.

## Source-file restrictions

Source files containing generation directives must be compiled unconditionally. Directives are unsupported in `_test.go` files, files with `//go:build` or `// +build` constraints, filenames that imply a GOOS/GOARCH constraint, and files that participate in cgo. Build constraints on source files that do not contain generation directives are supported.

For why these rules exist, see the [source restrictions](source-restrictions.md) document.

### Generation environment

`monoslices` scans all source files in the package, including those excluded by build constraints. Those files must parse successfully.

`monoslices` is assumed to be compiled under the same Go toolchain used to build the project. Using `go tool` to install and execute `monoslices` ensures this. If `monoslices` is installed as a raw binary, it should be rebuilt when changing toolchains.

Changing Go toolchains can change how the parser or filename classifier interprets source files. This can make previously generated code invalid. In this case, regenerate the `monoslices` output under the new toolchain.

### Build-specific specializations

Specialization functions may delegate to functions with build-specific definitions to implement build-specific specializations. For example:

```go
func compareRecord(a, b Record) int {
	return platformCompareRecord(a, b)
}

//monoslices:generate name=Records cmp=compareRecord
```

`platformCompareRecord` may have different implementations in constrained source files. `Record` may also have different build-constrained definitions.

## Package source handling

All non-test source files considered by `monoslices` must belong to one package. `monoslices` includes all declarations in the package to check generated code for name collisions, including `_test.go` files and conditionally-compiled files with the same package name. `_test.go` files in an external test package are excluded.

Package-scope declarations must not shadow predeclared Go identifiers used by generated code. The current set includes: `bool`, `clear`, `false`, `int`, `iota`, `len`, `panic`, `true`, `uint`, and `uint64`. It may be expanded in the future.

When generation directives are present, files in the package must not use dot imports.

## Generated-name conflicts

Before writing output, `monoslices` validates generated declarations against:

- source package declarations;
- other declarations generated by the same invocation;
- imports with explicit aliases.

`monoslices` does not validate generated declarations against default import package names. Conflicts can be addressed by providing explicit aliases.

Separate directives may use the same `name` so long as they do not generate the same declaration.

For example:

```go
//monoslices:generate name=Records cmp=byID ops=sort
//monoslices:generate name=Records cmp=byName ops=binary-search
```

is valid because `RecordsSort` and `RecordsBinarySearch` are each generated by only one directive. By comparison:

```go
//monoslices:generate name=Records cmp=byID ops=sort
//monoslices:generate name=Records cmp=byName ops=sort
```

is invalid because both directives would generate `RecordsSort`.
